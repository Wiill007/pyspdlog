# 17. Design notes

How pyspdlog works inside, the problems found while building it and how they were
solved, and the known limitations. Read this before changing the C++ code.

## Architecture

```text
pyspdlog/                    Python package
├── __init__.py              re-exports _core; atexit and register_at_fork hooks
├── handler.py               SpdlogHandler (logging → spdlog)
├── _core.abi3.so            the nanobind extension (spdlog + fmt compiled in)
├── _core.pyi                type stub generated by nanobind stubgen at build time
└── py.typed
```

| Source | Contents |
| --- | --- |
| `src/cpp/common.h` | shared declarations, the `LevelArg` type caster, the threading rules |
| `src/cpp/module.cpp` | `NB_MODULE`, enums, `SpdlogError`, `level_from_str` |
| `src/cpp/logger.cpp` | `Logger`, `AsyncLogger`, `log_message()` |
| `src/cpp/sinks.cpp` | all sinks, including the Python-backed ones and `LogMessage` |
| `src/cpp/registry.cpp` | registry, factories, global settings, module-level logging |
| `src/cpp/threads.cpp` | thread pool, periodic flusher, `shutdown()`, fork handlers |

### Build

- spdlog 1.17.0 is downloaded by CMake `FetchContent` from the release tarball, verified
  with SHA-256, and compiled as a static library with `-fPIC`. Downloading the tarball
  instead of cloning means building from the sdist does not need git.
- The extension is compiled with hidden symbol visibility and its own nanobind domain
  (`NB_DOMAIN pyspdlog`). Another extension that also embeds spdlog or nanobind cannot
  clash with it.
- `STABLE_ABI`: on Python 3.12+ the module targets the limited API, so one `abi3` wheel
  works on every later version. 3.10 and 3.11 get regular wheels.
- The `.pyi` stub is generated by importing the built module (`nanobind_add_stub`).

## How a message flows

```text
log.info("x={}", x)
 │  [GIL held]
 ├─ logger.should_log(INFO) or backtrace on?        → no: return (no formatting)
 ├─ async logger whose pool is gone?                → yes: drop (see "fork" below)
 ├─ text = "x={}".format(x)  →  UTF-8 bytes
 │  [GIL released]
 └─ spdlog::logger::log(level, text)                → sinks: pattern + I/O
```

The message is formatted **in Python** with `str.format()` and passed to spdlog as an
already-formatted string. spdlog never parses user text as an fmt format string, so a
`{` in a message cannot cause a format error inside spdlog, and Python objects get
their own `__format__`.

The log methods have positional-only `msg` (and `level`). In nanobind that means
unnamed `nb::arg()` annotations; `nb::sig` provides the signature shown in stubs and
`help()`. As a result `info("{level}", level=1)` works.

## Threading rules

These invariants make the extension deadlock-free. They are repeated at the top of
`common.h`:

1. **Never wait on a spdlog mutex while holding the GIL.** spdlog holds its mutexes
   (registry, sink, queue, backtracer) while it runs sinks, and Python sinks need the
   GIL. Every binding that may lock releases the GIL first (`release_gil` call guard,
   which converts arguments before releasing and return values after reacquiring).
2. **Python sinks never hold their own mutex while calling Python.** `python_sink`
   locks only around pattern formatting, unlike spdlog's `base_sink`, which locks for
   the whole write. A callback can therefore log, even to the same logger.
3. **Code that touches Python from spdlog threads uses `nb::detail::cleanup_guard`.**
   It attaches a thread state, or skips the work if the interpreter is gone.
4. **Never join a background thread from itself.** `shutdown()`, `init_thread_pool()`
   and `flush_every()` check thread-local flags set on pool and flusher threads.
5. **Globals used by background threads are heap-allocated and never freed**, so they
   stay valid during static destruction.

In a Python sink, the callable is copied to a local strong reference before the call,
so releasing the sink during the call (at exit) cannot free it mid-call.

## Problems found while building it

### 1. Reference cycles that the garbage collector cannot see

Python wrapper → C++ logger → sink (`shared_ptr` holding a Python reference) → Python
callback → … → the wrapper. The middle links are C++ references, invisible to the GC.
It took nothing exotic to trigger: a module-level callback function and a module-level
logger form such a cycle through the module's globals. nanobind's leak checker
reported it at exit.

**Considered:** `tp_traverse` / `tp_clear` on `Logger`, making the C++ edges visible.
**Rejected**, because a C++ logger can have owners that Python does not see (the
registry through `shared_from_this`, messages in the async queue). The GC could then
decide a logger is garbage and clear its callbacks while it is still in use.

**Solution:** every Python-backed sink registers itself in a global set. At exit,
after `shutdown()` has stopped all background threads, `_release_python_sinks()` takes
the Python references out of every sink, which breaks the cycles, and drops them
outside the lock. Cycles in short-lived loggers stay uncollectable until exit, as
documented.

### 2. `fork()` hung the child process

The child inherits the C++ thread pool and periodic flusher but not their threads.
Two failures followed: an inherited async logger queued messages nobody processed and
blocked forever once the queue filled up, and `shutdown()` at exit joined threads that
did not exist, which hung forever.

**Solution** (`threads.cpp`, plus `os.register_at_fork()` in `__init__.py`):

- Thread pools are numbered as they are created, and a counter records the first pool
  still alive. Async loggers whose pool number is below it drop messages.
- In the child, the inherited pool and flusher are deliberately leaked (never joined),
  the registry's pool is reset so new async loggers get a fresh one, and every
  inherited pool is marked dead. The first message dropped because of a fork issues a
  `RuntimeWarning`.
- Before the fork, the flusher's locks are taken (with the GIL released, because the
  flusher may need the GIL to finish), so the child never inherits them locked.

### 3. `spdlog::async_logger` is `final`

The first fork fix subclassed `async_logger` to remember its pool. That does not
compile: the class is `final`, and its pool pointer is private. **Solution:** a side
table maps each async logger pyspdlog creates (including `clone()`s) to its pool
number. It holds `weak_ptr`s, so a stale entry for a reused address is recognised and
ignored. The table is only consulted after a pool has died, so normal logging pays
only one atomic load.

### 4. spdlog's periodic flusher

`spdlog::flush_every()` flushes while holding the registry lock. A flush callback
calling `pyspdlog.get()` would deadlock, and the flusher cannot be abandoned after a
fork. **Solution:** pyspdlog has its own flusher thread. It copies the registered
loggers under the registry lock, flushes them outside it, and can be paused across
`fork()`.

### 5. Async `flush()` did not wait

In spdlog 1.17, `async_logger::flush()` only queues a flush request. **Solution:** a
barrier. pyspdlog queues one marker message per worker thread into a sink that blocks
until all markers have arrived. A worker blocked on a marker cannot take another
message, so each marker lands on a different worker. When all have arrived, everything
queued before them has been processed. A worker never waits for its own pool.

### 6. Null default logger crashes

`spdlog::get_level()`, `spdlog::should_log()` and `spdlog::dump_backtrace()` dereference
the default logger without checking it, so they would segfault after `drop_all()`. The
bindings reimplement them with a check, and module-level logging is a no-op without a
default logger.

### 7. Lifecycle calls from background threads

A callback calling `shutdown()` on a pool thread would make the thread join itself,
which ends in `std::terminate`. **Solution:** thread-local flags on pool and flusher
threads, and a `RuntimeError` for the calls that would join.

### 8. Noise at exit

- Logging to an async logger after `shutdown()` printed spdlog's
  `thread pool doesn't exist anymore` error for every message, which daemon threads do
  at exit. Async loggers bound to a stopped pool now drop messages quietly.
- nanobind's leak report always lists objects used by daemon threads, which the user
  cannot fix. It is off unless `PYSPDLOG_LEAK_WARNINGS` is set. The tests set it, so
  real leaks are still caught. `NB_DOMAIN` keeps the setting from affecting other
  nanobind extensions.

### 9. `None` as a message

nanobind rejects `None` for `nb::handle` parameters unless they are annotated with
`.none()`. The message parameter is annotated that way, so `log.info(None)` logs
`None`.

## Known limitations

- **Windows is not supported**: no CI, no wheels.
- **macOS is untested.** It is not in CI (GitLab's hosted macOS runners need a paid
  tier) and has not been tried yet. The code avoids Linux-only APIs, so it is expected to
  work: build it and run the tests on a Mac before relying on it.
- **No free-threaded Python** (3.13t, 3.14t), and no PyPy.
- **No source locations**: `%s`, `%#`, `%!`, `%@` and `%g` are empty.
- **Sinks are fixed** when a logger is created. spdlog's sink list is not thread-safe to
  modify, so it is not exposed.
- **No custom formatters or flag handlers** from Python, only patterns.
- **Not exposed:** syslog, systemd, `dist_sink`, `dup_filter_sink`, custom error
  handlers, `wchar_t` filenames, `_st` (single-threaded) sink variants.
- **Fork handling is best effort**: a lock held by another thread at the moment of the
  fork stays locked in the child.
- **No PyPI release yet.** Intel macOS and aarch64 Linux wheels are not built by default.
